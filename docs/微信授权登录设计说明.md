# 微信授权登录功能 · 设计说明

> 本文档说明「高中刷题小程序」微信授权登录的前后端配合、数据库持久化、完整流程与异常处理。
> 涉及云函数：`login`（改造）、`updateProfile`（新增）；数据库集合：`users`（新增）。

---

## 一、总体设计思路

微信小程序的「授权登录」分两层，二者解耦、各司其职：

1. **静默登录（免授权弹窗）**：调用 `wx.cloud.callFunction({ name: 'login' })`，云函数通过 `cloud.getWXContext()` 直接拿到 `openid / unionid / appid`。这一步**不需要用户点任何授权按钮**，用于建立用户身份、做数据隔离。
2. **资料授权（用户主动填写）**：头像、昵称属于用户隐私，微信自 2022 年 10 月 25 日后已**下线 `wx.getUserProfile`**，改为「头像昵称填写能力」——
   - 头像：`<button open-type="chooseAvatar">`，用户主动选择（微信默认带出当前头像）；
   - 昵称：`<input type="nickname">`，用户主动填写（键盘上可一键带出微信昵称）。
   - 二者都**不强制**：用户拒绝/跳过也能正常使用小程序，只是昵称头像为空、显示默认占位。

这样设计的好处：登录（拿 openid）与授权（拿头像昵称）分离，避免「用户拒绝授权就不能用」的强绑定体验。

## 二、数据表字段设计

### 2.1 用户表 `users`（新增）

以 **`openid` 作为文档主键 `_id`**，与业务表 `userId` 字段天然对齐，查询用户信息只需 `doc(openid)` 一次定位。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 主键 = openid（唯一） |
| `openid` | string | 微信 openid（同一小程序内唯一标识用户，冗余存储便于查询） |
| `unionid` | string | 微信 unionid（跨应用统一身份，**非必填**，见 4.2） |
| `appid` | string | 当前小程序 AppID |
| `nickname` | string | 昵称（用户主动填写，可为空） |
| `avatarUrl` | string | 头像（云存储 `cloud://` fileID，可为空） |
| `role` | string | 用户身份：`student`（默认）/ `teacher` / `admin`，用于区分身份与后续权限 |
| `status` | string | 账号状态：`active` / `banned`，可做封禁、风控 |
| `loginCount` | number | 累计登录次数（重复登录幂等计数） |
| `firstLoginAt` | Date | 首次登录时间 |
| `lastLoginAt` | Date | 最近一次登录时间 |
| `createdAt` / `updatedAt` | Date | 创建 / 更新时间 |

### 2.2 业务关联表（沿用现有，关联键统一为 `userId` = openid）

业务数据通过 `userId` 字段关联到 `users._id`（即 openid），**每个云函数都从 `cloud.getWXContext()` 取 `OPENID` 作为 `userId` 写入/过滤**，从源头保证用户数据隔离、可追溯：

| 集合 | 关联字段 | 说明 |
|---|---|---|
| `answer_records` | `userId` | 答题记录，按用户隔离 |
| `mistake_book` | `userId` | 错题本，按用户隔离 |
| `mastery` | `userId` | 知识点掌握度，按用户隔离 |

隔离与追溯的三重保障：
1. **写入侧**：`submitAnswer` 等云函数一律用服务端 `OPENID` 写 `userId`，前端无法伪造他人身份；
2. **读取侧**：`getStats` / `getMistakes` 等一律 `where({ userId: OPENID })`，只能读到本人数据；
3. **权限侧**：所有读写均走云函数，客户端不直连数据库（沿用项目现有约定）。

### 2.3 推荐索引

| 集合 | 索引 | 类型 |
|---|---|---|
| `users` | `openid` | 唯一索引（主键已保证） |
| `users` | `unionid` | 普通索引（跨应用身份查询） |

> 其余业务表索引沿用 `database/README.md` 既有定义，无需改动。

## 三、完整登录流程

```
启动 App
  │  onLaunch → wx.cloud.init({ env, traceUser: true })
  ▼
静默登录  login 云函数
  │  服务端 getWXContext() → { OPENID, APPID, UNIONID }
  │  users.doc(OPENID).get()
  ├─ 不存在 ──► 首次登录：set 新建用户记录，isNewUser = true
  └─ 已存在 ──► 重复登录：update（loginCount+1、lastLoginAt=now），isNewUser = false
  ▼
返回 { ok, openid, unionid, appid, isNewUser, user:{ nickname, avatarUrl, role, ... } }
  │  前端缓存到 app.globalData（openid / userInfo / isNewUser）
  ▼
业务页面（首页/答题/统计/错题本）
  │  调用 ensureLogin() 拿到 openid → 云函数按 userId=OPENID 读写本人数据
  ▼
「我的」页展示头像 / 昵称 / openid
  ├─ 未完善资料 ──► 提示「点击完善资料」→ 跳 profile 页
  └─ 已完善     ──► 展示头像昵称，可点击进入编辑
```

### 3.1 资料授权子流程（profile 页）

```
进入 profile 页（预填已有昵称头像）
  ├─ 选头像：button open-type="chooseAvatar" → 得到本地临时路径
  ├─ 填昵称：input type="nickname" → 用户填写
  ▼
点「保存」
  ├─ 有新头像 → wx.cloud.uploadFile 上传到云存储（avatars/{openid}_{ts}.ext）→ 得到 cloud:// fileID
  ├─ 调用 updateProfile 云函数（{ nickname, avatarUrl: fileID }）
  │    服务端校验昵称长度、头像 fileID 前缀 → 写入 users
  ▼
成功 → app.setUserInfo() 更新本地缓存 → 返回「我的」页即时刷新展示
```

### 3.2 前后端配合一览

| 环节 | 前端 | 后端（云函数） |
|---|---|---|
| 静默登录 | `wx.cloud.callFunction({name:'login'})` | `login`：getWXContext + users upsert |
| 保存资料 | `wx.cloud.uploadFile` + `callFunction({name:'updateProfile'})` | `updateProfile`：校验 + 写 users |
| 读用户信息 | `app.getUserInfo()`（本地缓存） | —（登录时已一次性返回） |
| 业务读写 | `callFunction({name:'submitAnswer'...})` | 各业务云函数按 `OPENID` 隔离 |

## 四、异常情况处理

### 4.1 授权失败 / 用户拒绝

- **静默登录**：`login` 云函数不依赖用户授权，几乎不会因授权失败。若网络/云函数异常，`app.login()` 捕获后返回 `{ ok: false }`，`loginPromise` 置空以便下次重试；`ensureLogin()` 返回空串，业务页面据此降级（不崩溃、可稍后重试）。
- **资料授权**：用户点「暂不完善」或直接返回，**不阻断任何功能**——昵称头像为空，前端展示默认占位头像与「同学你好」，后续随时可回「我的 → 完善资料」补填。
- 头像上传失败（网络抖动）：`profile.js` 捕获异常 `wx.showToast('保存失败，请重试')`，不写入半成品数据。

### 4.2 信息缺失（重点：unionid 拿不到）

`unionid` 是**条件性字段**，仅当满足以下任一条件时 `getWXContext()` 才返回 `UNIONID`：
- 小程序已绑定「微信开放平台」账号；
- 用户关注了与小程序同主体的公众号等。

因此：**unionid 设计为可空、非必填**。处理策略：
- 首次登录拿不到 → `unionid` 存空串；
- 后续某次登录满足条件拿到 → `login` 云函数检测 `UNIONID && !userDoc.unionid` 时补写；
- 前端/文档不把 unionid 当唯一标识，唯一标识始终是 openid（或 users._id）。

同理，`openid` 是兜底必填项：若 `getWXContext()` 异常返回空（理论上不会发生），云函数返回 `{ ok:false, code:'NO_OPENID' }`，前端不继续写入业务数据。

### 4.3 重复登录 / 并发登录

- **幂等 upsert**：`login` 云函数先 `get` 再 `set`/`update`，同一用户反复登录**不会产生重复记录**，只会 `loginCount` 递增、`lastLoginAt` 刷新。
- **前端防并发**：`app.login()` 用 `loginPromise` 缓存 in-flight 请求，多页面同时 `ensureLogin()` 只会发起一次真实调用，避免并发重复建号。
- **极端竞态兜底**：`updateProfile` 在用户记录不存在时也会 `set` 建号，保证「先调资料、后调登录」的异常顺序下也不会丢用户。

### 4.4 非法输入防护

| 输入 | 校验 |
|---|---|
| 昵称 | 去首尾空格、非空才写、长度 ≤ 32，超长返回 `INVALID_NICKNAME` |
| 头像 | 仅接受 `cloud://` 开头的云存储 fileID，防止写入任意外链，否则返回 `INVALID_AVATAR` |
| 空提交 | 无任何待更新字段时返回 `EMPTY`，避免无意义写库 |

## 六、部署与验证步骤

1. 在微信开发者工具中，右键 `cloudfunctions/login` 与 `cloudfunctions/updateProfile` → 「上传并部署：云端安装依赖」。
2. 重新运行一次 `initData` 云函数（幂等，会自动创建 `users` 集合）。
3. 编译预览 → 打开「我的」页：应看到默认头像 + 昵称「同学你好」+ 脱敏 openid。
4. 点击头像/「完善资料」进入 profile 页：选头像、填昵称、保存，返回「我的」页即时刷新展示。
5. 在云开发控制台查看 `users` 集合：确认已生成一条记录（`_id` = 你的 openid），重复进入小程序确认 `loginCount` 递增且不新增重复文档。
